Time: 6 minutes · Win: expose a read-only lookup without handing the model a database

Two different things

ToolDependency
A function the model may request. Its annotations and docstring describe the callable interface. The framework validates arguments and passes the returned value back to the model. A Python object your application passes into a run. It can hold a database adapter, HTTP client, or configuration — including credentials. The model never receives the dependency object itself.
Owned by the model's proposal layer. Owned by your application's permission and credential layer.

Pydantic AI validates tool arguments and passes dependencies through RunContext. Tools · Dependencies

from dataclasses import dataclass
from pydantic_ai import Agent, RunContext

@dataclass
class Notes:
    by_topic: dict[str, str]

agent = Agent(
    "test",
    deps_type=Notes,
    instructions="Find a note only when the user asks for one.",
)

@agent.tool
def find_note(ctx: RunContext[Notes], topic: str) -> str:
    """Find a note by its exact topic name."""
    if topic not in ctx.deps.by_topic:
        return "No note matches that topic."
    return ctx.deps.by_topic[topic]

result = agent.run_sync(
    "Find the note named 'NYC'.",
    deps=Notes({"NYC": "Use official city sources."}),
)

The model sees the tool name, description, argument schema, and returned value. It does not receive the Notes object itself.

Design the seam

  1. One read or one action. Write a normal function that does a single, bounded thing. Do: fetch one note by topic. Don't: "search my whole life and decide what to do."
  2. Bounded inputs. Give it typed inputs with bounded choices where possible. Do: Literal["on","off"]. Don't: a free-text entity ID the model can redirect to any device.
  3. Dependencies for clients and config. Put HTTP clients, configuration, and credentials in a dependency object passed by the app. Do: pass an httpx.AsyncClient and token through RunContext. Don't: hardcode secrets in tool code or prompt wording.
  4. Return only the evidence needed. Return the smallest result that answers the question. Do: a snippet with a source pointer. Don't: the full mailbox or raw device state the model doesn't need.
  5. Raise real failures. Don't disguise errors as successful empty results. Let the surface show an explicit limitation so the answer is honest.
  6. Read-only by default. The first version of any tool reads; write actions need a separate application-level approval step.
  7. Test with fakes first. Exercise the tool with fake data or a fake HTTP client before any live model or API call.

Use @agent.tool_plain when the function needs no run context. Use @agent.tool when it needs typed dependencies passed through RunContext.

Tool output is not trusted instruction. Email and web text can contain malicious directions. Keep permissions in code, not in prompt wording.

Self-check

Why pass a client through dependencies?

It makes the resource explicit, replaceable in tests, and controlled by the app. It keeps secrets and connection setup out of model-facing instructions.
