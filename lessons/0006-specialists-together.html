Time: 5 minutes · Win: choose a simple, least-privilege architecture

Do not start with a mega-agent

Build and test the Gmail reader, home controller, and NYC specialist independently. A deterministic app route can select among them. This keeps private email, physical controls, and public data from sharing unnecessary tools.

Pydantic AI documents several levels of multi-agent complexity, from a single agent to delegation and graphs. Its delegation example passes usage to the child and applies request limits. Multi-agent applications

When delegation earns its cost

  • One request genuinely needs two specialist outputs.
  • The orchestrator has a fixed list of allowed specialists.
  • Each child receives only the data and tools needed for its task.
  • The whole workflow has request and token limits.
  • Tests prove the correct specialist ran and no extra tool ran.

If those conditions are absent, call the chosen agent directly from Python. More agents mean more model calls, more latency, and more chances to expose data.

Basic delegation shape

from pydantic_ai import Agent, RunContext, UsageLimits

nyc_agent = Agent("provider:model", output_type=str)
router = Agent(
    "provider:model",
    instructions="Delegate NYC questions only to the NYC specialist.",
)

@router.tool
async def ask_nyc(ctx: RunContext[None], question: str) -> str:
    """Ask the NYC specialist one focused question."""
    result = await nyc_agent.run(question, usage=ctx.usage)
    return result.output

result = await router.run(
    "What do these NYC 311 records say?",
    usage_limits=UsageLimits(request_limit=4),
)

This is a structural example, not a complete router. Replace "provider:model" with a supported model and pass only the dependencies the child needs.

Specialist blueprint

  1. Job: one sentence naming the user task. Good: "Answer NYC 311 questions from official city data." Bad: "help the user with anything."
  2. Sources: official or owner-approved inputs. Name the exact dataset, endpoint, or archive, and who approved it.
  3. Tools: only operations needed for that job. One read-only search tool, not a grab bag of capabilities.
  4. Output: answer plus evidence, date, and uncertainty. Cite source_url and retrieved_at; say what the data cannot show.
  5. Denied abilities: explicit list, enforced in Python. If it's not on the allow-list, the model cannot call it — no matter what the prompt says.
  6. Tests: one normal case, one missing-source case, one boundary case. All run with fake services; no live mailbox, device, or endpoint.

Self-check

Should one default agent receive Gmail search and smart-home tools?

No. Keep those permissions in separate agents. Route to a capability only when the user's request requires it.
