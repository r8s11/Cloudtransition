Build order

  1. Write one job and one observable success condition.
  2. Choose the narrowest authoritative data source.
  3. Write a normal Python function that reads or acts safely.
  4. Expose that function as a typed agent tool.
  5. Pass clients and settings through typed dependencies.
  6. Return a structured result when another program must use the answer.
  7. Test with fake dependencies before any live model or API call.
  8. Add approvals and usage limits before expanding permissions.

Agent anatomy

user request
    ↓
typed Pydantic AI agent
    ↓ selects a tool and arguments
application-owned tool function
    ↓ validates scope, calls one adapter
Gmail archive | Home Assistant | official NYC source
    ↓ returns bounded evidence
agent answer + source / uncertainty

The Python application owns credentials, permissions, validation, and side effects. The model proposes tool calls; it does not become the authorization layer.

Core API shape

agent = Agent(
    "provider:model",
    deps_type=Services,
    output_type=Answer,
    instructions="One job. State limits. Cite evidence.",
)

@agent.tool
async def lookup(ctx: RunContext[Services], query: str) -> Evidence:
    """Fetch bounded, trusted evidence for the request."""
    ...
  • Agent defines one behavior and the types it needs.
  • RunContext[Services] gives a tool application-owned dependencies.
  • A tool docstring and type annotations define the model-facing tool contract.
  • output_type validates shape, not truth. Validate sources and behavior separately.

Alexa boundary

Amazon's Smart Home Skill API describes Alexa calling a device provider's skill so Alexa can control devices that provider exposes. It is not evidence of a general API for commanding any device already linked to a consumer's Alexa account. An agent needs a supported device API or a bridge such as Home Assistant that already controls that entity.
